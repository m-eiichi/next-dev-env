# 02 仕組み

## 1. AI が読むもの

```
CLAUDE.md   → 「@AGENTS.md」（AGENTS.md を読み込む）と、Claude Code だけの仕組み（skill、hook）の案内
AGENTS.md   → 毎回読み込まれる入口。毎回守ることと、作業ごとに読む資料（docs/ の節）の目次
docs/       → ルールの本体。作業に関係する資料を、その都度読む
.claude/    → skill（必要なときに読み込む手順書）と hook（自動で動く処理）
```

| ファイル | 読まれるタイミング | 書くこと | 書かないこと |
| -------- | ------------------ | -------- | ------------ |
| `CLAUDE.md`（Claude Code が読む） | 毎回 | 先頭の `@AGENTS.md` と、Claude Code だけの仕組み（skill、hook）の案内 | どの AI にも共通のルール（Claude Code 以外の AI ツールは AGENTS.md を読むので、AGENTS.md に書く） |
| `AGENTS.md`（多くの AI ツールが読む） | 毎回 | どの AI にも共通の、機械では止められず毎回守ってほしいこと、作業ごとに読む資料の目次、作業を終える前のチェック | ルールの中身の要約（`docs/` の写しになる）。ESLint などが止めるルール（「1.1」） |
| `docs/` | 作業に関係するとき | ルールの本体、理由（ADR） | - |
| `node_modules/next/dist/docs/` | Next.js の機能を使うとき | （Next.js の公式の資料。このバージョンの正しい書き方） | - |

- AGENTS.md の先頭の Next.js についての段落は、`next dev` が書き足すもの。消しても元に戻るので、そのまま残す
- この 2 つの組み合わせ（AGENTS.md と、それを読み込む CLAUDE.md）は、Next.js が作る形と同じ（`node_modules/next/dist/server/lib/generate-agent-files.js`）。CLAUDE.md を消すと Claude Code がルールを読まなくなり、`next dev` も作り直さないので、消さない

### 1.1 読ませ方（Progressive Disclosure）

AI に最初から全部を読ませず、**作業に必要になった分だけを、段階的に読ませる**（[ADR-014](../04_設計判断/ADR-014_段階的に読ませる.md)）。毎回読まれるものを小さく保つほど、作業に関係する資料に注意を向けられる。

| 段階 | 読まれるタイミング | 置くもの | 置かないもの |
| ---- | ------------------ | -------- | ------------ |
| 1. 入口 | 毎回 | `CLAUDE.md`・`AGENTS.md`、skill の説明文（`description`）。**機械では止められず、毎回必ず守ってほしいこと**と、**作業ごとにどの資料を読むかの目次** | ルールの中身の説明。ESLint・ls-lint・hook が止めるルール（止められたときに、エラーの文から資料をたどれる） |
| 2. 作業の手順 | その作業をするとき | skill の本文（`SKILL.md`）。全体の流れと、場合ごとにどの詳しい手順を読むか | 場合によって要らない手順の中身 |
| 3. 詳しい手順・ルール | その場合・その節が必要になったとき | skill の `references/`、`docs/` の各資料の該当する節 | - |

- 入口の目次は「作業 → 資料の節」の形で書く（例: 「取得・キャッシュを書く → 04 データ取得・更新の「1」「2」」）。資料名だけでなく節まで示し、長い資料を丸ごと読まずに済むようにする
- 入口にルールを足したくなったら、まず ESLint などで機械的に止められないかを考え、止められないものだけを入口に書く
- skill の本文が長くなったら、場合ごとの手順を `references/` に分け、本文には「どの場合にどれを読むか」だけを残す

## 2. 仕組みの一覧

### 2.1 skill（`.claude/skills/`）

決まった手順の作業を、必要なときだけ読み込む手順書。ふだんの作業の流れ（作る → 確かめる → コミット）の順に並べ、ときどき行う作業をその後に置く。

| skill | 使う場面 | 中身 |
| ----- | -------- | ---- |
| `add-feature` | 新しい画面、または画面に出すデータ（取得・更新）を追加するとき | 本文（`SKILL.md`）は全体の流れと、場合ごとに読む手順の案内。詳しい手順は `references/` の `backend.md`（バックの読み取り。query）・`frontend.md`（フロント）・`mutation.md`（更新がある場合。command）・`client-fetch.md`（TanStack Query を使う場合）・`touch-points.md`（コードのほかに直す場所。`remove-sample` と共用）。ルールは `docs/` へのリンク |
| `app-check` | 画面を作った・変えた後に、動くかを確かめるとき。`add-feature` の仕上げでも使う | ビルド結果（○ / ◐ / ƒ）の見方、アプリを起動して画面を開き必ず止めるスクリプト（`scripts/check-pages.mjs`。コンテナに `ps` / `pkill` がないため）、`<Suspense>` の中の 404 の見分け方、knip が失敗したときの案内 |
| `commit` | コミットを頼まれたとき。作業の報告の後に「問題なければコミットしますか？」と尋ね、OK をもらったとき（`CLAUDE.md` の案内。どちらでもなければ使わない） | 変更の確かめ方、コミットするファイルの決め方（ステージ済みを優先、分けるときの提案）、メッセージの作り方（ルールは [08 コーディング規約](../02_共通設計/08_コーディング規約.md) の「5.1」。Issue のための変更なら `(#12)` を付ける）、`git commit` の権限の確認をメッセージの承認として使う流れ |
| `remove-sample` | 実装の見本（メモ・TODO など）を消すとき。`add-feature` で本来の最初の画面を作るときにも声をかける | 消す前に確かめること、参照の洗い出し（`grep`）、消す順番、仕上げ。消す場所の一覧は `add-feature` の `references/touch-points.md` を逆にたどる |
| `rename-term` | 画面に出す言葉（画面名、用語）を変えるとき。`add-feature` で、新しい言葉がすでにある言葉とぶつかるときや、見本を作り変えるときにも使う | 変える範囲の決め方（日本語の表記だけ変え、URL とコード上の名前は残すのが基本）、洗い出し、SCR のファイル名とリンクの直し方、仕上げ |
| `issue` | 課題（GitHub Issues）を作る・親とサブイシューに分ける、次にやることを答える、Issues とロードマップのずれを直す（棚卸し）とき | `gh` が使えるかの確かめ方、Issue を作る手順（似た Issue を探す、案を見せて OK をもらう、本文は標準入力で渡す）、分けるときに Issue の作成とロードマップの追加を同じ作業で行う流れ、「次は何？」で先にずれを確かめる流れ、棚卸しで探すずれと直し方の表。ルールは [06_課題・ロードマップ](../06_課題・ロードマップ/README.md) へのリンク |
| `update-ai-docs` | AI の仕組み（`.claude/` の skill・hook・権限、`AGENTS.md`、`CLAUDE.md`）を追加・変更・削除したとき | 変えたものの確かめ方（`git diff`）、変えたものごとに直す資料の表（この資料の節、`CLAUDE.md` の案内、`01 方針・進め方`、ディレクトリ構成など）、資料と実際の設定の突き合わせ方 |

- skill は Claude Code を立ち上げたときに読み込まれる。追加・変更したら、次の会話から使える

### 2.2 hook（`.claude/settings.json`、`.claude/hooks/`）

決まったタイミングで、必ず動く処理。

| hook | タイミング | すること |
| ---- | ---------- | -------- |
| ESLint（`eslint-changed-file.mjs`） | ファイルを編集・作成した後（`Edit` / `Write`） | 編集したファイルが `src/` の `.ts` / `.tsx` なら ESLint をかける。エラーがあれば Claude に伝えて直させる |
| 資料をそろえる案内（`remind-ai-docs.mjs`） | ファイルを編集・作成した後（`Edit` / `Write`） | 編集したファイルが AI の仕組み（`.claude/`、`AGENTS.md`、`CLAUDE.md`）なら、skill `update-ai-docs` で資料をそろえるよう Claude に伝える（止めはしない）。`.claude/settings.local.json` は個人の設定なので対象外 |

- 確認や一時的な停止は、Claude Code の `/hooks` から行う

### 2.3 権限（`.claude/settings.json` の `permissions`）

AI が確認なしで実行してよいもの、必ず人に確認するもの、実行させないものを分ける。判定は `deny` → `ask` → `allow` の順で、先に当たったものが使われる。

| 区分 | 対象 | 理由 |
| ---- | ---- | ---- |
| 読めない（`deny`） | `.env*`（`.env.example` を除く）。書き方は `Read(.env*)` の後に `Read(!.env.example)` | 秘密の情報を AI に読ませない（[01 方針・進め方](./01_方針・進め方.md) の「4」）。Claude の読み込み・検索・編集と、Bash の `cat` などに効く。`grep -r` や、テストのコードが中で開くファイルには効かないので、レビューで見る |
| 読めない・実行させない（`deny`） | `gh` のトークン: `~/.config/gh/` の読み込み、`gh auth token`、`gh auth status -t` / `--show-token` | `gh` のログインのトークンは `~/.config/gh/hosts.yml` に平文で置かれる。AI は `gh` のコマンドは使えるが、トークンの中身を会話に出さない。`.env*` と同じく、`grep -r` などには効かない |
| 実行させない（`deny`） | `git add -f` / `--force`（オプションの位置ごとに書く） | Git が無視している `.env*` などをステージさせない。AI にさせる場面はないので、必要なら人が行う。`git add -Af` のようにまとめた書き方には当たらない |
| 編集させない（`deny`） | `node_modules/` | AI が依存を直接直す正しい場面はない（`pnpm install` で消える）。書き換えるなら、テストを通すためのごまかしになる。読むのは今までどおりできる。依存を直すなら、人が `pnpm patch` で行う |
| 確認なし（`allow`） | ふだん作業する場所の編集: `src/`、`docs/`、`public/`、`README.md` | 作業のたびに直す場所 |
| 確認なし（`allow`） | `pnpm lint` / `lint:ls` / `typecheck` / `test` / `test:coverage` / `build` / `knip` | 作業ごとに何度も流すチェック。手元のファイルしか変えない。`pnpm test` 以外は引数のない形だけを許可しているので、`--fix` などを付けると確認が出る。`npx eslint` は `--fix` や `-o` で確認が必要なファイルも書き換えられるので許可しない（編集したときの ESLint は hook が流す） |
| 確認なし（`allow`） | `git status` / `git diff` / `git log` / `git add` | 読むだけか、戻せる操作（ステージ）。skill `commit` で、確認を `git commit` の 1 回にまとめるため |
| 確認なし（`allow`） | `gh issue list` / `gh issue view`、`gh auth status`（引数なし） | GitHub の Issues を読むだけ。skill `issue` の棚卸しなどで何度も読むため。読むだけの確認が続くと、書き込みの確認も中身を見ずに許可する癖がつくので、確認を書き込みだけに絞る |
| 必ず確認（`ask`） | AI の縛りや指示の編集: `.claude/`（skill・hook・`settings.json`・`settings.local.json`）、`AGENTS.md`、`CLAUDE.md` | AI が自分の権限や指示を変えられないようにする。`.claude/` は Claude Code が最初から守っている場所で、手動と編集の自動承認のモードでは `allow` に書いても確認が出る。`ask` に書くのは、auto モードでも確認を出すため |
| 必ず確認（`ask`） | `.git/` の編集 | `.git/hooks/` に、Git の操作のたびに動く処理を仕込めるため。最初から守られている場所だが、auto モードでも確認を出すために書く |
| 必ず確認（`ask`） | チェックの設定の編集: `*.config.*`（ESLint、Vitest、Next.js など）、`knip.json`、`.ls-lint.yml`、`tsconfig.json`、`.github/`（CI） | チェックを通すために、ルールのほうを緩めないようにする |
| 必ず確認（`ask`） | 依存・環境の編集: `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`components.json`、`scripts/`、`.devcontainer/`、`.env*`、`.gitignore` | 依存の変更は人に確認する作業。環境や秘密の情報に関わる（`.gitignore` の `.env*` の行を消すと、秘密の情報がコミットに入りうる） |
| 必ず確認（`ask`） | `docs/04_設計判断/` の編集 | 採用済みの ADR は書き換えない（`docs/` のほかの場所は確認なし。`ask` が `allow` より優先される） |
| 必ず確認（`ask`） | 削除（`rm` / `rmdir`）、`git reset` / `git clean` | 戻せない変更 |
| 必ず確認（`ask`） | `pnpm test` の `-u` / `--update`（スナップショットの更新） | 期待値を今の結果で上書きして、テストを弱められる（[01 方針・進め方](./01_方針・進め方.md) の「4」） |
| 必ず確認（`ask`） | Bash でのファイルの書き換え（`cp` / `mv` / `sed -i`） | 編集の自動承認モードでは、これらが確認なしで通り、上書きもできるため |
| 必ず確認（`ask`） | `git checkout` / `git restore` / `git stash` | まだコミットしていない変更を消したり、見えなくしたりする。ブランチの切り替えも確認する |
| 必ず確認（`ask`） | `git commit` | 頼まれていないコミットはしない（[01 方針・進め方](./01_方針・進め方.md)） |
| 必ず確認（`ask`） | `git push` | 外に出る。頼まれていない push はしない（[01 方針・進め方](./01_方針・進め方.md)） |
| 必ず確認（`ask`） | 依存の追加・削除・更新（`pnpm add` / `remove` / `update`、`npm install` / `uninstall`） | 依存の変更は人に確認する作業。`pnpm install`（lockfile どおりに入れる）は含めない |
| 必ず確認（`ask`） | GitHub への書き込み（`gh`）: `gh issue` の `create` / `edit` / `close` / `reopen` / `comment` / `delete` / `transfer` / `lock` / `unlock` / `pin` / `unpin` / `develop`、`gh label`、`gh api`、`gh auth` の `login` / `logout` / `refresh` / `setup-git` / `switch`、`gh pr` / `repo` / `project` / `release` / `workflow` / `run` / `secret` / `variable` / `gist` / `browse` | 外に送った内容は、消しても残ることがある。読むだけの `gh issue list` / `view` を確認なしにするため、`gh *` をまとめて `ask` にせず、書き込むものを並べている（`ask` は `allow` より優先される）。ここにない `gh` のコマンドは、既定どおりその都度確認になる。`gh` のコマンドが増えたら見直す |
| 必ず確認（`ask`） | 外部サービス: `curl` / `wget`、`WebFetch`、MCP（Claude Docs、Gmail、Google Calendar、Google Drive） | 外に送った内容は、消しても残ることがある |

- 上のどちらにもないものは、Claude Code の既定どおり、その都度確認する
- 編集の場所は `Edit(場所)` で書く（`Edit` と `Write` の両方に効く）。場所を付けない `"Edit"` / `"Write"` は、どこでも書けてしまうので `allow` に入れない
- 新しいフォルダ（`e2e/` など）をふだんの作業場所にするなら、`allow` に `Edit(フォルダ/**)` を足す
- 個人だけの設定（よく使うコマンドを許可するなど）は `.claude/settings.local.json` に書く（Git で管理しない）
- MCP のサーバーを足したら、`ask` に `mcp__サーバー名` を足す
- `settings.json` の権限を変えたら、VS Code の「Developer: Reload Window」で読み込み直すまで効かない（会話を始め直すだけでは読み込まれなかった）

#### 最初のモード

Claude Code の VS Code の拡張機能は、最初のモードを「Edit automatically」（`acceptEdits`）に固定している（`.devcontainer/devcontainer.json` の `claudeCode.initialPermissionMode`）。

- 理由: Claude Code 2.1.283 からは、何も決めていないと auto モードで始まる。auto モードでは、`allow` にも `ask` にもないコマンドを、確認の代わりに判定の AI が通すかを決める。`ask` はコマンドの文字で当てるので、`git -C . push` のような別の書き方で抜けると、公開リポジトリに頼んでいない push が出るおそれがある
- このモードでは、作業フォルダの中の編集と `mkdir` / `touch` などが確認なしで通る。上の表の `ask` と `deny` は効く（確かめ済み）
- プロジェクトの `.claude/settings.json` の `defaultMode` は、VS Code では最初のモードに使われないため、`devcontainer.json` に書いている
- auto モードを使うなら、先に、コマンドの中身を見て `push` などに確認を出す hook（PreToolUse）を作る

### 2.4 AI 以外でも効く仕組み

AI 専用ではないが、AI の変更も同じように止める仕組み。

| 仕組み | 止めること | 資料 |
| ------ | ---------- | ---- |
| ESLint | 層をまたぐ import、ファイル直下のアロー関数 など | [06 アーキテクチャ](../01_全体設計/06_アーキテクチャ.md) の「依存の向き」、[08 コーディング規約](../02_共通設計/08_コーディング規約.md) |
| ls-lint | ファイル名・フォルダ名のルール違反 | [05 ディレクトリ構成](../01_全体設計/05_ディレクトリ構成.md) の「4」 |
| テスト | 業務のルールとユースケースの誤り。層の説明ページのコード例と実際のコードのずれ | [10 テスト](../02_共通設計/10_テスト.md) |
| knip | 使っていないファイル・export・依存（わざと置いているものは `knip.json` で外し、指摘 0 件を保つ） | [11 CI](../02_共通設計/11_CI.md) の「3.3」 |
| CI | 上のすべて（Pull Request ごと） | [11 CI](../02_共通設計/11_CI.md) |

## 3. 仕組みを足すとき

### 3.1 どれを使うか

| やりたいこと | 使うもの | 例 |
| ------------ | -------- | -- |
| 毎回必ず守ってほしく、機械では止められない短いルール | `AGENTS.md` に 1 行足し、詳しくは `docs/` にリンク | 「画面から `fetch("/api/...")` で自前の API を呼ばない」 |
| Claude Code だけの仕組みの案内 | `CLAUDE.md` に 1 行足す | 「画面を追加するときは skill `add-feature` に沿う」 |
| 決まった手順の作業 | skill | 画面を追加する手順 |
| 必ず動かしたい、数秒で終わる処理 | hook | 編集したファイルの ESLint |
| 機械で判定できるルール | ESLint・ls-lint・テスト（AI 以外にも効く） | 層をまたぐ import の禁止 |
| 役割を分けた補助の AI | agents（`.claude/agents/`） | まだ使っていない。必要になってから |

- 機械で判定できるものは、AGENTS.md や skill に書くより、ESLint やテストで止める方を優先する
- `.claude/rules/` は使わない。ルールは `docs/` に 1 か所だけ置く（[ADR-013](../04_設計判断/ADR-013_AI駆動開発の資料.md)）

### 3.2 足すときのルール

- skill・AGENTS.md・CLAUDE.md には手順と案内だけを書き、ルールの中身は `docs/` へのリンクにする（写さない）
- hook は数秒で終わるものにする。ビルドやテスト全体のように時間がかかるものは、作業を終える前に流す（AGENTS.md の「作業を終える前に」）
- hook のスクリプトは Node.js で書く（開発用のコンテナに必ず入っているため。`jq` などは入っていない）
- チームで共有する設定は `.claude/settings.json`（Git で管理する）。個人の設定は `.claude/settings.local.json`（Git で管理しない）
- 足したら、この資料の「2. 仕組みの一覧」に書き足す。足す・変える・消したときに直す資料は、skill `update-ai-docs` にまとめている

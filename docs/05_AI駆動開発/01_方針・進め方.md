# 01 方針・進め方

## 1. 方針

| 方針 | 内容 |
| ---- | ---- |
| ルールの本体は `docs/` の 1 か所 | 人も AI も同じ資料を読む。AI 専用の場所（`.claude/` など）にルールを写さない（写すと食い違う） |
| AI 専用の設定は最小限 | AI だけが使うもの（手順書の skill、自動で動く hook）だけを `.claude/` に置く（[02 仕組み](./02_仕組み.md)） |
| 決めたことは、なるべく機械で止める | 指示で守らせるより、ESLint・ls-lint・テスト・hook で止める方が確実。止められないものだけを資料と指示で守る |
| 決めるのは人、形にするのは AI | 何を作るか・方針をどうするかは人が決める。AI は案を出し、決まったことを資料とコードにする |

## 2. 人と AI の役割分担

| 作業 | 人 | AI |
| ---- | -- | -- |
| 要件（何を作るか） | 決める | 質問や、足りない点の指摘 |
| 方針・設計（ADR） | 案を選んで決める | 案を並べ、良い点・悪い点を示す。決まったら ADR を書く |
| 資料（00〜03、05） | 確認する | 実装の前に更新する |
| 実装・テスト | レビューする | 資料どおりに書き、テストを足す |
| CI と同じチェック | CI の結果を確認する | 作業を終える前に流す |
| コミット・push・Pull Request・マージ | 行う（または AI に明示的に頼む） | 頼まれたときだけ行う |

## 3. 作業の流れ

```
1. 人が依頼する
2. AI が関係する資料を読む（AGENTS.md → docs/ の該当する資料）
3. 資料と違うやり方が必要なら、AI が人に確認する（案と理由を示す）
4. AI が資料を先に更新する（方針を変えるなら ADR も）
5. AI が実装し、テストを足す（編集のたびに hook が ESLint をかける）
6. AI が CI と同じチェックを流す
7. AI が報告する（変えたもの、更新した資料、確かめていないこと）
8. 人がレビューする（[03 レビュー](./03_レビュー.md)）
9. 人がコミット・マージする
```

- 新しい画面やデータを足すときは、skill `add-feature` の手順に沿う（[02 仕組み](./02_仕組み.md)）
- 依頼があいまいなとき（何を作るかで結果が大きく変わるとき）は、作り始める前に AI が確認する
- 決め方に迷うときは、AI が「おすすめ」を 1 つ示したうえで、人が選ぶ

### ADR の扱い

- 人が方針に同意してから、状態を「採用」にして書く。同意の前に残すなら「提案」にする
- 採用済みの ADR の本文は書き換えない（[04_設計判断/README](../04_設計判断/README.md)）。AI が方針を変えるときも、新しい ADR を作る

## 4. AI に任せないこと

| 任せないこと | 理由 |
| ------------ | ---- |
| 頼まれていないコミット・push・Pull Request の作成 | 変更を外に出すかどうかは人が決める |
| 依存の追加・削除を黙って行うこと | `package.json` の変更は影響が広い。理由を示して確認してから行う |
| 資料と違うやり方を、確認なしで採ること | 資料が正しい前提が崩れる |
| テストを通すために、テストやルールを弱めること（`eslint-disable`、期待値の書き換えなど） | 守るべきことが守られなくなる。必要なら理由を示して確認する |
| 秘密情報（`.env.local` の値、API キーなど）を読んで、資料・コード・会話に書くこと | 漏れるおそれがある |
| 本番環境の操作 | 取り返しがつかない |

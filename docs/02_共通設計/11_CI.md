## 1. 方針

| 項目 | ルール |
| ---- | ------ |
| 使うサービス | GitHub Actions |
| 設定ファイル | `.github/workflows/ci.yml` |
| 実行のタイミング | Pull Request の作成・更新時、`main` への push 時 |
| マージの条件 | CI が通っていない Pull Request は `main` にマージできない（「4. GitHub 側の設定」） |

## 2. 実行するもの

| 順番 | 実行するもの | コマンド | 失敗したとき |
| ---- | ------------ | -------- | ------------ |
| 1 | Lint | `pnpm lint` | マージできない |
| 2 | ファイル名のチェック | `pnpm lint:ls` | マージできない |
| 3 | 型チェック | `pnpm typecheck` | マージできない |
| 4 | テスト + カバレッジ | `pnpm test:coverage` | マージできない |
| 5 | ビルド | `pnpm build` | マージできない |
| - | 未使用コードの検出 | `pnpm knip` | 参考のみ（マージできる）。別のジョブで実行する |

- 1〜5 は 1 つのジョブ（`Lint / 型チェック / テスト / ビルド`）で順番に実行し、途中で失敗したらそこで止まる
- 同じブランチに新しく push されたら、実行中の CI は止めて新しい方だけを実行する
- Node.js のバージョンは Dev Container（`.devcontainer/Dockerfile`）と合わせる。片方を変えたら、もう片方も変える
- pnpm のバージョンは `package.json` の `packageManager` から読み込む

### 手元で同じチェックをする

Pull Request を出す前に実行しておくと、CI での失敗を減らせる。

```bash
pnpm lint && pnpm lint:ls && pnpm typecheck && pnpm test:coverage && pnpm build
```

## 3. 設定の理由

### 3.1 型チェックの前に `next typegen` を実行する

`pnpm typecheck` の中身は `next typegen && tsc --noEmit`。

| 理由 | 内容 |
| ---- | ---- |
| 型が自動生成される | `PageProps` / `LayoutProps` などの型と `next-env.d.ts` は、Next.js が `next dev` / `next build` / `next typegen` の実行時に作る |
| Git で管理していない | `next-env.d.ts` は `.gitignore` に入れている（Next.js の推奨）ため、CI の環境には存在しない |
| ビルドより速い | 型を作るためだけに `next build` を実行するより速い。Next.js の公式ドキュメントでも CI での型チェックにこの手順を推奨している |

### 3.2 テストが 0 件でも通す

`vitest.config.ts` で `passWithNoTests: true` にしている。

- Vitest はテストファイルが 1 つもないと失敗するため、テストを書き始める前の段階でも CI を通すための設定
- テストがそろってきたら外してもよい（外すと、テストファイルを誤って消したときに気づける）

### 3.3 未使用コードの検出（knip）は参考にとどめる

`ci.yml` の `knip` ジョブに `continue-on-error: true` を付けている。

- 導入したがまだ使っていないライブラリ（Font Awesome、React Hook Form など）があると、knip は失敗する
- 開発の初期は失敗が続くため、必須にするとマージが止まってしまう

**必須にするタイミング**: 主要な画面がそろい、knip の指摘が 0 件になったら `continue-on-error: true` を消し、「4. GitHub 側の設定」の必須のチェックにも `未使用コードの検出（参考）` を追加する（名前も変える）。

## 4. GitHub 側の設定

「CI が失敗したらマージできない」ようにするには、GitHub の画面での設定が必要（`ci.yml` だけでは止まらない）。

<!-- 設定したら、下の「設定状況」を更新する -->

### 4.1 手順

1. CI を 1 回動かす（Pull Request を作るか、`main` に push する）。一度動くまでは、手順 5 の選択肢にチェック名が出てこない
2. リポジトリの **Settings → Branches → Add branch protection rule**（または **Settings → Rules → Rulesets**）を開く
3. 対象のブランチに `main` を指定する
4. **Require a pull request before merging** をオンにする（`main` に直接 push できないようにする）
5. **Require status checks to pass before merging** をオンにし、`Lint / 型チェック / テスト / ビルド` を選ぶ
6. 保存する

### 4.2 設定状況

| 項目 | 状況 | 設定日 | 設定者 |
| ---- | ---- | ------ | ------ |
| Pull Request を必須にする | 未設定 / 設定済み | | |
| CI の通過を必須にする | 未設定 / 設定済み | | |

## 5. CI が失敗したとき

| 失敗した段階 | よくある原因 | 対処 |
| ------------ | ------------ | ---- |
| インストール | `package.json` を変えたのに `pnpm-lock.yaml` を更新していない | 手元で `pnpm install` を実行し、`pnpm-lock.yaml` もコミットする |
| Lint | 書き方のルール違反 | `pnpm lint` で確認して直す |
| ファイル名のチェック | ファイル名・フォルダ名がルールと違う | `pnpm lint:ls` で確認し、名前を直す。ルール自体を変えるなら [05 ディレクトリ構成](../01_全体設計/05_ディレクトリ構成.md) の「4. ファイル名のルール」を参照 |
| 型チェック | 型の間違い | `pnpm typecheck` で確認して直す |
| テスト | テストの失敗、カバレッジが 80% 未満 | `pnpm test:coverage` で確認する。カバレッジは [10 テスト](./10_テスト.md) の「7. カバレッジ」を参照 |
| ビルド | 環境変数の不足、Server / Client Component の使い分けの誤りなど | `pnpm build` で確認する。環境変数が必要なら GitHub の Secrets に登録し、`ci.yml` で渡す |

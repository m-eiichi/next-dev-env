## 1. テストの種類と使うツール

| 種類 | 対象 | ツール | 導入のタイミング |
| ---- | ---- | ------ | ---------------- |
| 単体テスト | ドメイン層（エンティティ、値オブジェクト）、ユースケース | Vitest | 最初から |
| コンポーネントのテスト | 表示だけのコンポーネント（DTO を受け取るもの）、フォームの操作 | Vitest + React Testing Library | コンポーネントのテストが必要になったら |
| 結合テスト | リポジトリの実装（DB とのやり取り、変換） | Vitest + テスト用の DB | DB が決まってから |
| E2E テスト | `async` の page、画面をまたぐ操作の流れ | Playwright | 画面が増えてきたら |

### Vitest でテストできないもの

`async` の Server Component（`await` でデータを取得する `page.tsx` など）は、Vitest ではテストできない（Next.js の公式ドキュメントより）。次のどちらかで対応する。

- 画面の中身を、DTO を受け取るだけの同期のコンポーネントに切り出し、そちらを Vitest でテストする
- 画面全体は E2E テストで確認する

## 2. 何をテストするか

| 対象 | テストする | テストしない |
| ---- | ---------- | ------------ |
| エンティティ・値オブジェクト | 業務のルール（正常な値、境界値、ルール違反で `DomainError` になること） | getter だけのもの |
| ユースケース | 手順（リポジトリが呼ばれるか）、認可（未ログイン・権限なしで失敗するか）、DTO への変換 | ドメインのルールの細かい組み合わせ（ドメインのテストで確認済み） |
| コンポーネント | 表示の分岐（空のとき、エラーのとき）、操作したときの動き | 見た目（色、余白） |
| Server Action / Route Handler | 原則テストしない（ユースケースを呼ぶだけなので） | - |

- 要件の「受け入れ条件」（[02 機能要件](../00_要件定義/02_機能要件.md)）を、テストケースの元にする

## 3. ファイルの置き場所と名前

| 種類 | 置き場所 | 名前 | 例 |
| ---- | -------- | ---- | -- |
| 単体・コンポーネント・結合 | テスト対象と同じフォルダ | `<対象のファイル名>.test.ts(x)` | `src/domain/post/entity.test.ts` |
| E2E | `e2e/`（プロジェクトの直下） | `<機能>.spec.ts` | `e2e/create-post.spec.ts` |

- `describe` にはテスト対象（クラス名、関数名）、`it` には「どうなるべきか」を日本語で書く

```ts
describe("PostTitle", () => {
  it("100 文字を超えると DomainError になる", () => {
    expect(() => PostTitle.of("あ".repeat(101))).toThrow(DomainError);
  });
});
```

## 4. 実行環境

| 対象 | 環境 | 指定のしかた |
| ---- | ---- | ------------ |
| ドメイン層、ユースケース、インフラストラクチャ層 | `node` | 初期値（指定しない） |
| コンポーネント | `jsdom` | ファイルの先頭に `// @vitest-environment jsdom` を書く |

## 5. モック

| 対象 | ルール |
| ---- | ------ |
| リポジトリ、`AuthService` | インターフェースを満たすオブジェクトを `vi.fn()` で作り、ユースケースのコンストラクタに渡す（[06 アーキテクチャ](../01_全体設計/06_アーキテクチャ.md) のコンストラクタインジェクション） |
| `server-only` | `vitest.config.ts` で空のモジュールに置き換える（テストのたびに書かない） |
| 日時 | `vi.useFakeTimers()` と `vi.setSystemTime()` で固定する |
| DI コンテナ、`vi.mock` でのモジュールの差し替え | なるべく使わない。コンストラクタで渡せば済むようにする |

- ドメイン層はモックを使わずにテストする（依存がないため）

## 6. 実行

| コマンド | 内容 |
| -------- | ---- |
| `pnpm test` | watch モードで実行する（開発中） |
| `pnpm test run` | 1 回だけ実行する |
| `pnpm test <ファイル名の一部>` | 一部のテストだけ実行する |
| `pnpm test:coverage` | 1 回だけ実行し、カバレッジも確認する（CI と同じ） |

| タイミング | 実行するもの |
| ---------- | ------------ |
| 開発中 | `pnpm test`（watch） |
| Pull Request / main への push | CI（GitHub Actions）で自動で実行する。**失敗したらマージできない**（[11 CI](./11_CI.md)） |
| リリース前 | E2E テスト（導入後） |

## 7. カバレッジ

| 項目 | ルール |
| ---- | ------ |
| 対象 | ドメイン層（`src/domain/`）とユースケース（`src/application/`）だけ |
| 目標 | 行・分岐・関数・文のそれぞれ **80% 以上**。下回ると CI が失敗する |
| 設定 | `vitest.config.ts` の `coverage.include` と `coverage.thresholds` |
| 確認方法 | `pnpm test:coverage`。結果は `coverage/` にも出力される |

- 画面とインフラストラクチャ層は、E2E テストと結合テストで確認するので、数値の目標から外している
- 数値を上げるためだけのテストは書かない。業務のルールと認可のチェックが網羅されていることを優先する

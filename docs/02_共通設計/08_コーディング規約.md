## 1. 命名

| 対象 | ルール | 例 |
| ---- | ------ | -- |
| コンポーネント | PascalCase（ファイル名は kebab-case。[05 ディレクトリ構成](../01_全体設計/05_ディレクトリ構成.md) の「4. ファイル名のルール」） | `UserCard`（ファイルは `user-card.tsx`） |

| Server Action | 動詞で始める | `createPost`, `deleteUser` |

## 2. TypeScript

| 項目 | ルール |
| ---- | ------ |
| `strict` | 有効のまま（`tsconfig.json`） |
| `any` | 使わない。どうしても必要なら `unknown` にして絞り込む |
| 型の定義 | `type` / `interface` のどちらかにそろえる |
| page / layout の props | Next.js が生成する `PageProps<'/path'>` / `LayoutProps<'/path'>` を使う |
| 関数の書き方 | 下の「2.1 関数の書き方」 |

### 2.1 関数の書き方

ファイル直下の関数（コンポーネントを含む）は `function` で書く（[ADR-011](../04_設計判断/ADR-011_関数の書き方.md)）。

| 場所 | 書き方 | 例 |
| ---- | ------ | -- |
| ファイル直下の関数（export するもの・しないもの、どちらも） | `function` | `export function PostList() {}`、`export default async function Page() {}` |
| 関数の中で作る関数（イベントハンドラー、コールバックなど） | アロー関数でよい | `const handleClick = () => {}`、`items.map((item) => ...)` |
| オブジェクトの中の関数 | アロー関数でよい | `export const container = { postRepository: () => new PostRepositoryImpl() }` |
| 関数式（`const f = function () {}`） | どこでも使わない | - |

- ESLint（`func-style` と `no-restricted-syntax`、`eslint.config.mjs`）でチェックする。`pnpm lint` でエラーになる
- shadcn/ui が作る部品も `function` で書かれているので、そのままでよい

## 3. React・Next.js

| 項目 | ルール |
| ---- | ------ |
| `'use client'` | 必要な最小の部品にだけ付ける。ページ全体に付けない |
| メモ化 | React Compiler が有効なので、`useMemo` / `useCallback` / `memo` は原則書かない |
| 画像 | `<img>` ではなく `next/image` を使う |
| リンク | 画面内の移動は `<a>` ではなく `next/link` を使う |
| 非推奨 API | `middleware.ts` は使わず `proxy.ts` を使う |
| クラス名の結合（`cn()`） | `cn` パッケージから直接 import する（`import { cn } from "cn"`）。shadcn/ui で追加した部品と同じ書き方にそろえる |

- `src/lib/utils.ts`（`export { cn } from "cn"`）は、shadcn/ui の CLI のための中継ぎなので、自分のコードからは使わない。ただし消さない。`components.json` の `aliases.utils` がこの場所を指していて、CLI は部品を追加するときに `cn` の import をここへ書き換えることがあるため（`@/lib/utils` を前提にした部品を追加したときに壊れないようにする）

## 5. Git

| 項目 | ルール |
| ---- | ------ |
| ブランチ | `main` + 作業ブランチ（`feature/xxx`, `fix/xxx`）。どのブランチで作業するかは人が決める |
| AI のコミット | 今のブランチにコミットする。ブランチを切るかは確かめない（`main` の上でもそのままコミットし、報告にブランチ名を書く）。push は頼まれたときだけ |
| コミットメッセージ | Conventional Commits の形で、日本語で書く（下の「5.1」） |
| マージ | Pull Request を作り、CI が通り、レビューを受けてからマージする |

### 5.1 コミットメッセージ

AI にコミットを頼むときは、skill `commit` がこのルールでメッセージを作る。

**形**

```
<種類>: <何をしたか>

- <主な変更 1>
- <主な変更 2>
```

- 1 行目だけでよい。変更が複数あるときだけ、空行の後に本文を箇条書きで書く
- 共同作成者の行（`Co-Authored-By:`）は付けない

**種類**

| 種類 | 使うとき | 例 |
| ---- | -------- | -- |
| `feat` | 画面・機能の追加や変更（使う人から見て変わるもの） | `feat: TODO の詳細画面を追加` |
| `fix` | 不具合の修正 | `fix: 完了済みの TODO を完了にできてしまう不具合を修正` |
| `refactor` | 動きを変えないコードの整理 | `refactor: 在庫の計算をドメイン層に移動` |
| `test` | テストだけの追加・修正 | `test: メモのタイトルの境界値のテストを追加` |
| `docs` | `docs/`、`README.md`、コメントだけの変更 | `docs: SCR-020 のファイル名を今の名前に修正` |
| `ci` | CI（`.github/workflows/`）と、CI で流すチェックの変更 | `ci: knip を必須のチェックに追加` |
| `chore` | 依存、ツールの設定（`knip.json`、ESLint など）、Claude Code の設定（`.claude/` の skill・hook・権限） | `chore: skill commit を追加` |

- 変更が複数の種類にまたがるときは、一番主な変更の種類にする（画面を足して資料も直したなら `feat`。資料の更新は付随するものとして同じコミットに入れる）
- 関係のない変更が混ざっているときは、コミットを分ける

**1 行目**

- 日本語で、「〜を追加」「〜を修正」「〜に変更」「〜を削除」のように、何をしたかで終える。文末に句点（。）を付けない
- 60 文字くらいまで。長くなるなら、細かいことは本文に回す
- コード上の名前・ツール名は英語のまま書き（`knip`、`Server Action`、`SCR-040`）、日本語との間に半角スペースを入れる（資料の書き方と同じ）
- 1 行目ではバッククォートを使わない（`git log --oneline` で読みやすくするため）

**本文**

- 箇条書きは `- ` で始める。文末に句点を付けない
- 「何を変えたか」と、わかりにくいものは「なぜ」を書く。3〜7 行くらい。ファイルを 1 つずつ並べない
- コード上の名前はバッククォートで囲んでよい

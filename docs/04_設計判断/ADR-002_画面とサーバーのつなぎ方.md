# ADR-002 画面の取得・更新は Server Component / Server Action で行い、API Route は外部公開だけに使う

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-23 |
| 決めた人 | |

## 背景

層を分けた構成（[ADR-001](./ADR-001_コードの層分け.md)）で、画面からユースケースをどう呼ぶかを決める必要があった。参考にした既存プロジェクト（RootLog）では、画面から `fetch` で API Route を呼び、API Route からユースケースを呼んでいた。

## 決定

- 画面の表示に使うデータは Server Component で、更新は Server Action で、ユースケースを直接呼ぶ
- Route Handler（API Route）は、外部公開 API（`/api/v1/`）、Webhook（`/api/webhooks/`）、画面から使うどうしても必要なもの（`/api/internal/`、ファイルのダウンロードなど）だけに使う
- 画面から外部公開 API を呼ばない

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. Server Component / Server Action（採用） | 最初からデータ入りの HTML を返せるので表示が速い。書くコードが少ない（1 操作あたり約 2 ファイル）。型が関数としてそのままつながる。`'use cache'` やストリーミングなど Next.js の機能を使える | Next.js 専用で、他のアプリから呼べない |
| B. すべて API Route 経由 | 境界がはっきりする。スマホアプリなど他からも呼べる。バックエンドを切り出しやすい。curl などで単体で確認できる | 初回表示でローディングが挟まる（PC で約 0.1〜0.3 秒、スマホで約 0.3〜1 秒以上遅い見積もり）。1 操作あたり約 4 ファイル。JSON を経由するので実行時に型が保証されない |
| C. A を基本にし、外部に必要なものだけ API Route | A の速さと少なさを保ったまま、外部公開にも対応できる | 画面用と外部用で入口が 2 種類になる |

## 理由

- 今のところ、Next.js 以外（スマホアプリなど）から使う予定がない
- 処理の中身はユースケースにあり、入口は薄いので、後から外部公開 API が必要になっても `route.ts` を足すだけで済む（C の形になる）
- 一般ユーザーがスマホで開く画面では、B の初回表示の遅れが体感できる大きさになる

### 画面から外部公開 API を呼ばない理由

画面と外部の利用者が同じ API を使うと、「画面の都合で API を変えたいが、外部の利用者がいるので変えられない」という状況が生まれるため。

## 影響

- 画面から `fetch('/api/...')` で自前の API を呼ばない
- TanStack Query は、クライアントで再取得やポーリングが必要な場合だけに使う
- **見直す条件**: スマホアプリなど Next.js 以外のクライアントを作ることになった、またはバックエンドを別のサーバーに分けることになった場合

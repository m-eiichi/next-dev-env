# ADR-001 コードを DDD・クリーンアーキテクチャで層に分ける

| 項目 | 内容 |

| 状態 | 採用 |
| 日付 | 2026-09-23 |

## 背景

Next.js の App Router では、page や Server Action の中に DB へのアクセスや業務のルールを直接書けてしまう。規模が大きくなると、同じルールがあちこちに書かれて食い違ったり、認可のチェックが漏れたり、DB を使わずにテストできなかったりする。

## 決定

- コードを ドメイン層 / アプリケーション層（ユースケース）/ インフラストラクチャ層 / プレゼンテーション層 に分け、依存は外側から内側への一方向だけにする
- ユースケースは依存（リポジトリなど）をコンストラクタで受け取る
- 依存の組み立ては入口（Server Component / Server Action / Route Handler）で、DI コンテナから実装を取り出して行う
- DI コンテナは呼ぶたびに新しいインスタンスを返す

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 層に分ける（採用） | 業務のルールが 1 か所に集まる。DB なしでテストできる。DB や認証サービスを差し替えやすい | ファイルが増える。小さな機能でも手順が多い |
| B. page / Server Action に直接書く | 書く量が少なく、始めるのが速い | ルールや認可のチェックが散らばる。テストしにくい |
| C. データアクセス層（DAL）だけ分ける（Next.js 公式の推奨） | A より軽く、認可のチェックを 1 か所にまとめられる | 業務のルールの置き場所が決まらず、DAL が大きくなりがち |

## 理由

- テンプレートとして、中〜大規模に育つことを前提にした
- 参考にした既存プロジェクト（RootLog）で同じ構成を採用しており、考え方を共有できる
- Next.js 公式の DAL の考え方（サーバーだけで動く、認可をチェックする、DTO を返す）は、ユースケースに担わせることで取り込める

### DI コンテナを呼ぶたびに新しいインスタンスにした理由

参考にした構成では、static なクラスでインスタンスを使い回していた。サーバーではインスタンスがリクエストをまたいで共有されるため、ユーザーごとの情報を持つ実装を使い回すと、別のユーザーに情報が漏れるおそれがある。

## 影響

- ドメイン層では Next.js、React、DB クライアント、Zod を import しない
- 小さな機能ではファイルが多くなりすぎるため、読むだけの機能などは一部を省略してよい（ただし認可のチェックと DTO への変換は省略しない）
- テストの中心は、ドメイン層とユースケースの単体テストになる（[ADR-005](./ADR-005_テストツール.md)）

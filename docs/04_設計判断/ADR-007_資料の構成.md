# ADR-007 資料を要件定義・全体設計・共通設計・画面設計に分ける

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-23 |
| 決めた人 | |

## 背景

最初の資料の構成では、目的・スコープ・非機能要件などの要件が「全体設計」の中に、システム構成などの設計と混ざって置かれていた。要件定義をどこに置くかを決める必要があった。

## 決定

`docs/` を次の 4 つ（+ この設計判断）に分ける。

| フォルダ | 内容 |
| -------- | ---- |
| `00_要件定義/` | 何を・誰のために・なぜ作るか |
| `01_全体設計/` | どう作るかの全体像 |
| `02_共通設計/` | 画面をまたぐ実装のルール |
| `03_画面設計/` | 画面ごとの詳細 |
| `04_設計判断/` | 決めたことの理由 |

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 全体設計の中に置いたまま | フォルダが少ない。変更がいらない | 依頼者と合意する内容（要件）と、開発者が決める内容（設計）が混ざる |
| B. 要件定義のフォルダを分ける（採用） | 確認する相手ごとに資料を渡しやすい。どこまで決まっているかが見やすい。要件定義 → 基本設計 → 詳細設計という一般的な流れと対応する | フォルダ名と番号が変わり、リンクの書き直しが必要 |

## 理由

- 要件は依頼者・企画担当と合意するもので、設計は開発者が決めるもの。確認する相手とタイミングが違う
- 「何を作るか」が固まってから「どう作るか」を決める、という順番がフォルダの番号で表せる

## 影響

- 資料の追加・削除のルールは [docs/README.md](../README.md) の「資料を書くときのルール」に従う
- ADR（このフォルダ）は、「どうするか」を書いた 00〜03 の資料とは分け、理由だけを残す

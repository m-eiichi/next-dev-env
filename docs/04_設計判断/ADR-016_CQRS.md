# ADR-016 アプリケーション層を更新（command）と読み取り（query）に分ける（CQRS）

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-26 |
| 決めた人 | |

## 背景

入口はすでに、取得（`src/server/entry/queries/`）と更新（`src/server/entry/actions/`）に分かれていた（[ADR-008](./ADR-008_フロントとバックの分け方.md)）。一方で、アプリケーション層から内側は分かれておらず、読み取りも更新も同じユースケースの書き方で、同じリポジトリを使っていた。

この形のままだと、読み取りのための機能（一覧用の結合、件数、並べ替え、ページ分け）がリポジトリとエンティティにたまっていく。業務のルールを守るためのエンティティが、画面の都合でふくらむことになる。[06 アーキテクチャ](../01_全体設計/06_アーキテクチャ.md) の「8. 小さな機能での省略」には「読むだけならリポジトリが DTO を直接返してよい」とあったが、例外の扱いで、決まりにはなっていなかった。

## 決定

- アプリケーション層を、更新（`src/server/application/command/`）と読み取り（`src/server/application/query/`）に分ける
- 更新は、今までどおりユースケースがエンティティ・値オブジェクトとリポジトリ（ドメイン層）を使い、業務のルールを守る
- 読み取りは、ドメイン層を通らず、読み取り専用のインターフェース（Query Service）から DTO を直接受け取る。Query Service の実装はインフラストラクチャ層に置き、結合やページ分けを直接書いてよい
- 読み取りでも、認証・認可のチェックは必ずクエリで行う
- DB は 1 つのまま（読み取り用のデータを別に持たない）
- サンプルは、今ある読み取りを query 側に移したうえで、サンプルの「登録」を足し、command 側の見本にする

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. コードの中で分ける（段階 1。採用） | エンティティとリポジトリが更新のためだけのものになり、ふくらまない。読み取りは画面に要る形で素直に書ける。DB を増やさなくてよい | 1 つのデータにつき、リポジトリと Query Service の 2 つの実装を書く。読み取りと更新で同じ条件（公開済みかどうか など）を 2 か所に書くことがある |
| B. 分けない（今のまま） | ファイルと考え方が少ない | 読み取りのための機能がリポジトリとエンティティにたまる |
| C. 読み取り用のデータを別に持つ（段階 2） | 読み取りを大きく速くできる | 更新のたびに読み取り用のデータを作り直す仕組みが要る。今の規模には重い |
| D. イベントソーシング（段階 3） | 変更の履歴をすべて残せる | 仕組みが大きく、このプロジェクトの規模には重すぎる |

## 理由

- 業務のルールを持つのは更新だけで、読み取りに要るのは画面の形。求められるものが違うので、モデルを分けた方がどちらも素直に書ける
- 入口はすでに取得と更新に分かれているので、アプリケーション層から内側を分けるのは自然な延長になる
- DB がまだ決まっていないうちに決めておけば、最初の本物の機能から、この形で作れる
- 「8. 小さな機能での省略」の例外（読むだけならリポジトリが DTO を返してよい）を、決まりとして整理できる

## 影響

- 読み取りのユースケースは「クエリ」と呼び、`src/server/application/query/{エンティティ名}/{名前}.query.ts` に置く。更新は今までどおり「ユースケース」と呼び、`src/server/application/command/{エンティティ名}/{名前}.usecase.ts` に置く
- ドメイン層のリポジトリには、更新に要るメソッド（保存、削除、更新のための取得）だけを置く
- DI コンテナは、1 つのデータにつきリポジトリと Query Service の 2 つを返す
- ESLint で、command と query が互いに import しないようにする。インフラストラクチャ層は、Query Service を実装するために `src/server/application/query/` のインターフェースと DTO を import してよい
- 読み取りと更新で同じ条件を 2 か所に書く場合（公開済みだけを返す、など）は、条件をドメイン層の関数・定数にして、両方から使う
- **見直す条件**: 読み取りが重くなり、画面の表示が遅くなった場合（案 C を検討する）。Query Service とリポジトリの 2 つを書く手間が、得られるものより大きく感じられるようになった場合

# ADR-014 AI に読ませる情報を段階に分ける（Progressive Disclosure）

| 項目 | 内容 |

| 状態 | 採用 |
| 日付 | 2026-09-26 |

## 背景

AI が毎回読む入口（`CLAUDE.md` ＋ `AGENTS.md`）は約 3,800 字あり、その大半が `docs/` のルールの要約だった。要約は `docs/` の写しなので、2 か所に書いている状態でもあった（[ADR-013](./ADR-013_AI駆動開発の資料.md) で避けると決めたこと）。

一方で、ルールの本体の資料は長いものがある（`06_アーキテクチャ.md` は約 25,000 字）。入口には「どの資料を読むか」までしか書いておらず、1 つのルールを確かめるために長い資料を丸ごと読むことがあった。skill `add-feature` も、更新（Server Action）や TanStack Query を使う場合の手順が 1 行ずつしかなく、場合によって必要な情報が足りなかった。

## 決定

- AI に読ませる情報を、入口（毎回）→ 作業の手順（skill の本文）→ 詳しい手順・ルール（skill の `references/`、`docs/` の節）の 3 段階に分ける
- 入口（`AGENTS.md`）には、機械では止められず毎回守ってほしいことと、「作業 → 読む資料の節」の目次だけを書く。ルールの中身の要約は書かない
- skill `add-feature` は、本文に全体の流れと場合ごとの案内だけを残し、詳しい手順を `references/` に分ける

段階の分け方と、それぞれに何を置くかは [02 仕組み](../05_AI駆動開発/02_仕組み.md) の「1.1」に書く。

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 入口を目次にし、skill を分ける（採用） | 毎回読む量が減り、`docs/` との二重の書き方もなくなる。場合ごとの手順を詳しく書ける | 入口だけを読んでもルールの中身はわからない。資料を読みに行く手間が 1 回増える |
| B. 今のまま（入口にルールの要約を書く） | 入口だけでおおよそのルールがわかる | 毎回読む量が多い。`docs/` と食い違うおそれがある |
| C. A に加えて、長い資料（06 アーキテクチャ）を分ける | 必要な層の資料だけを読めるようになり、効果が一番大きい | 06 へのリンクが資料とコードのあちこちにあり、書き直しが多い |

## 理由

- 入口から外すルールのうち、層をまたぐ import・関数の書き方・ファイル名は、ESLint・ls-lint・hook が止める。止められたときのエラーの文から資料をたどれるので、入口に書いておく必要が薄い
- 目次に資料の「節」まで書けば、C のように資料を分けなくても、長い資料の必要な部分だけを読める
- C は効果が大きいが変更も大きいので、06 が実際に読みにくくなってから行う

## 影響

- 入口にルールを足すときは、まず機械で止められないかを考える。止められないものだけを入口に書く
- `docs/` の節の番号や名前を変えたら、`AGENTS.md` の目次も直す
- skill を足すときも、本文と `references/` に分ける
- **見直す条件**: 入口から外したルールの読み落としが目立つようになった場合（そのルールを入口に戻すか、機械で止める方法を考える）。06 アーキテクチャなど長い資料の節を探すのに手間がかかるようになった場合（案 C を行う）

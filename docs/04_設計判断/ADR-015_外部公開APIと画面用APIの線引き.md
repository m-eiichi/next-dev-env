# ADR-015 外部公開 API と画面用 API は、形式をそろえ、中身を分ける

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-26 |
| 決めた人 | |

## 背景

外部公開 API（`/api/v1/`）を REST で作る場合に、画面用の API（`/api/internal/`）のレスポンスもそれに合わせるべきかを検討した。

これまでに、公開用の型を DTO と分けること（[ADR-009](./ADR-009_APIのレスポンスの型.md)）と、失敗したときの形を RFC 9457 にそろえること（[ADR-010](./ADR-010_APIのエラーの形.md)）は決めていた。ただ、「何をそろえ、何を分けるか」の線引きは 1 か所にまとまっていなかった。また、[09 外部公開 API](../02_共通設計/09_外部公開API.md) の「1. 基本方針」には「画面と同じユースケースを呼ぶ」とあり、同じ資料の「9. 実装の例」（外部公開用のユースケースを呼んでいる）と食い違っていた。項目名（camelCase / snake_case）も決まっていなかった。

## 決定

- **形式**（書き方の約束）は、外部公開 API と画面用 API でそろえる: JSON、成功は `{ data }`、失敗は RFC 9457、ステータスコードの使い方、項目名、日時の書き方
- **中身**（何をどう返すか）は分ける: 返す項目、URL の設計、一覧のページ分け、バージョン、認証、互換性の約束
- 外部公開 API は、ユースケースが返す DTO を、入口（`src/server/entry/api/v1/`）で公開用の型に詰め替える
- 外部だけの取り方や項目が要るときは、画面用の DTO を広げず、外部公開用のユースケースを分ける
- 項目名は camelCase にする

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 形式はそろえ、中身は分ける（採用） | エラーを扱うコードなどを 1 種類で済ませられる。画面の変更が外部の利用者に漏れない | 公開用の型と詰め替えの関数を書く手間がある |
| B. 形式も中身もそろえる（画面用も外部公開用と同じ API にする） | 書く量が一番少ない | 画面の都合で項目を足す・消すと、外部の利用者を壊す。画面が外部公開 API を使う形になり、[ADR-002](./ADR-002_画面とサーバーのつなぎ方.md) で避けた状態になる |
| C. 形式も中身も分ける | 画面用を自由に作れる | エラーの形などが 2 種類になり、扱うコードも 2 種類になる（ADR-010 で避けたこと） |

### 項目名について

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| camelCase（採用） | TypeScript のコード、DTO、画面用の API と同じ書き方になる。詰め替えで名前を変換しなくてよい | snake_case に慣れた利用者（Ruby、Python など）には少し読みにくい |
| snake_case | 一部の言語の利用者に慣れた書き方 | 画面用の API と形式がそろわない。詰め替えのたびに名前を変換する必要がある |

## 理由

- 形式はほとんど変わらないので、そろえても困らない。中身は画面を直すたびに変わりうるので、分けておかないと外部の利用者を壊す
- 詰め替えは「結果を HTTP の形にする」入口の役割なので、ドメイン層やユースケースに外部への見せ方を持ち込まない
- 画面用の DTO に外部の都合の項目を足していくと、DTO が画面と外部の両方の都合でふくらみ、結局どちらの変更も難しくなる

## 影響

- 09 外部公開 API の「1. 基本方針」と「6」を、この決定に合わせて直す
- 外部公開 API を足すたびに、公開用の型と詰め替えの関数（`toPublic〇〇`）を書く
- **見直す条件**: 外部の利用者から snake_case を求められた場合（項目名だけを見直す）。外部公開 API の数が増え、公開用の型を手で書く負担が大きくなった場合（OpenAPI から型を作る形を検討する）

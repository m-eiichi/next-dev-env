# ADR-009 API のレスポンスの型を、呼び出し元とデプロイの関係で決める

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-23 |
| 決めた人 | |

## 背景

TanStack Query の見本（[SCR-011](../03_画面設計/SCR-011_サンプル検索.md)）を作ったとき、`/api/internal/examples` のレスポンスの型を、サーバー（入口）とブラウザ（Client Component）で別々に手で書いていた。サーバーで返す形を変えても、型チェックでは気付けない状態だった。

型を共有するとフロントとバックが強く結び付くのでは、という疑問もあった。しかし、型を別々に書いてもフロントがレスポンスの形に依存していることは変わらない。依存が見えなくなるだけで、結合が弱くなるわけではない。大事なのは、安定した約束（契約）だけに依存することであり、何を約束にするかは、呼び出し元とデプロイの関係で変わる。

## 決定

| 場合 | レスポンスの型 |
| ---- | -------------- |
| 画面用の Route Handler（`/api/internal/`） | 入口のファイルで export し、フロントは `import type` で使う（共有する） |
| 外部公開 API（`/api/v1/`） | DTO とは別に、公開用の型を作る。画面用の DTO をそのまま返さない |
| バックを別のサーバーに分けたとき | スキーマ（OpenAPI、Zod のスキーマなど）を約束にし、型はそこから作る。受け取る側で実行時にもチェックする |

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 呼び出し元とデプロイの関係で分ける（採用） | それぞれの場合で、ずれを防ぐのに必要な分だけの手間で済む | ルールが 3 通りになる |
| B. すべて型を共有する | 書く量が一番少ない | 外部公開 API で、画面の都合の変更が外部の利用者を壊す |
| C. すべて別々に書く | フロントとバックのコードが import でつながらない | 形がずれても気付けない。依存が消えるわけではない |
| D. 最初からすべてスキーマ（OpenAPI など）から作る | バックを分けても、そのまま使える | 同じリポジトリで一緒にデプロイしている今は、手間に見合わない |

## 理由

- `/api/internal/` は自分の画面だけが使い、同じリポジトリから一緒にデプロイする。フロントとバックが常に同じ版なので、TypeScript の型を共有すればずれを防げる
- 共有するのは、[ADR-008](./ADR-008_フロントとバックの分け方.md) でフロントとの約束にした入口（`src/server/entry/`）の型だけ。`import type` はビルド時に消えるので、サーバーのコードはブラウザに入らない
- 外部公開 API は、利用者のプログラムがこちらのデプロイとは関係なく動いている。画面用の DTO を返すと、画面の都合の変更がそのまま外部に漏れる（[09 外部公開 API](../02_共通設計/09_外部公開API.md) の「6」）
- バックを分けると、フロントとバックのデプロイの時期がずれる。TypeScript の型はビルド時にしかチェックされないので、実行時にチェックできるスキーマが必要になる

## 影響

- `/api/internal/` の入口では、レスポンスの型を export し、返す値に `satisfies` を付けて型と実装がずれないようにする
- 外部公開 API の公開用の型と変換の関数は、`src/server/entry/api/v1/` に置く
- **見直す条件**: バックを別のサーバーに分けることになった場合（[ADR-002](./ADR-002_画面とサーバーのつなぎ方.md) の「見直す条件」と同じ）。スマホアプリなど、同じリポジトリにないクライアントから `/api/internal/` を呼びたくなった場合（そのときは `/api/v1/` として公開する）

# ADR-010 API のエラーの形を RFC 9457（Problem Details）にそろえる

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-23 |
| 決めた人 | |

## 背景

外部公開 API（`/api/v1/`）のエラーは、[09 外部公開 API](../02_共通設計/09_外部公開API.md) で独自の形（`{ error: { code, message, details } }`）に決めていた。一方、画面用の Route Handler（`/api/internal/`）は `{ message }` を返していて、同じアプリの中にエラーの形が 2 通りあった。

そろえるにあたって、今の独自の形にそろえるか、HTTP の API のエラーの形として標準になっている RFC 9457 にするかを検討した。`/api/v1/` はまだ資料の例があるだけで実装がなく、今なら利用者を壊さずに形を変えられる。

## 決定

- `/api/v1/` と `/api/internal/` の失敗したときのレスポンスを、RFC 9457（Problem Details for HTTP APIs）の形にそろえる。`Content-Type` は `application/problem+json`
- 規格の項目は `type`（`about:blank`）、`title`、`status`、`detail` を使う
- 追加項目として、機械的に分岐するための `code` と、入力欄ごとのエラーを返す `errors` を付ける
- 成功したときの形（`{ data: T }`）は変えない

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. RFC 9457 ＋ `code` ＋ `errors`（採用） | 標準なので、外部の利用者が規格の知識で読める。対応したライブラリもある。`code` と `errors` で、独自の形でできていたことはすべてできる | 項目が少し多い。入力欄ごとのエラーの形は規格にないので、自分で決める必要がある |
| B. 独自の形（`{ error: { code, message, details } }`）にそろえる | 単純。資料ですでに決まっていた | 外部の利用者は、この API のためだけにエラーの形を覚える必要がある |
| C. RFC 9457 の項目だけ（`code` と `errors` を付けない） | 規格どおりで一番素直 | 何のエラーかを `type` の URI で表す必要があり、エラーごとに説明のページを用意しなければならない。入力欄ごとのエラーを返せない |

## 理由

- このテンプレートは、外部公開 API を作ることを前提に 09 の資料を用意している。外部の利用者にとっては、独自の形より標準の方が扱いやすい
- `/api/v1/` はまだ実装がないので、切り替えの手間が今だけで済む
- `type` に URI を付けて説明のページを用意するのは、今の段階では手間に見合わない。`about:blank`（HTTP のステータスコードの意味どおり、という規格の既定値）にして、何のエラーかは `code` で表す

## 影響

- 失敗したときのレスポンスは、`src/server/entry/api/problem-details.ts` の `problemResponse()` で作る。`/api/v1/` と `/api/internal/` で共用する
- `title` はステータスコードの英語の名前（`Bad Request` など）、`detail` は利用者向けの日本語のメッセージにする
- `errors` は `code` が `VALIDATION_ERROR` のときだけ付ける
- **見直す条件**: エラーごとに説明のページ（`type` の URI）を用意できるようになった場合（そのときは `type` を使い、`code` との関係を決める）

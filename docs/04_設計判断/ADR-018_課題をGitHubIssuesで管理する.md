# ADR-018 課題を GitHub Issues で管理し、ロードマップだけをプロジェクト内に置く

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-10-03 |
| 決めた人 | |

## 背景

課題や新機能の要望が増えてきたときに、何があって、どの順で進め、今どこまで進んだかを把握する場所がなかった。`docs/` には決まった要件と設計しかなく、大きな改修を分けたときのまとまりや順序、改修と課題のつながりも残せなかった。

## 決定

- 課題の中身・状態・親子・依存は GitHub Issues（サブイシュー、依存関係、ラベル、必要なら Projects）に書く
- `docs/06_課題・ロードマップ/` には、Issues の使い方のルールと、大きなまとまりの順序（ロードマップ）だけを置く。各課題の状態は書かない
- コミットメッセージに `(#12)`、Pull Request に `closes #12` を書いて、課題と変更をつなぐ

## 検討した案

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. プロジェクト内のファイルだけ | AI が追加の道具なしで読める。課題の変化もコミットに残る | 状態の更新が手作業。PR がマージされても課題は閉じない。GitHub の画面で見られない |
| B. ファイルを正にし、GitHub Actions で Issues に写す | 今のファイルのまま、GitHub の画面でも見られる | 写すスクリプトと workflow を持つ必要がある。Issues 側で直した内容はファイルに戻らない |
| C. Issues を正にし、ロードマップだけファイルに残す（採用） | PR・コミットと自動でつながり、マージで閉じる。サブイシューと依存関係で、分け方と順序を GitHub の機能で表せる。他の人も GitHub 上で参加できる | AI が読むには `gh` が要る。課題の情報がリポジトリの外にあり、オフラインでは見られない |
| D. Issues とファイルの両方を正にして同期する | どちらからでも書ける | ずれやぶつかりが起きやすい |

## 理由

- 課題と Pull Request・コミットのつながりを、手作業なしで残したい
- 毎日変わる状態は Issues に、めったに変わらない順序と目的はプロジェクト内に置けば、同じことを 2 か所に書かずに済む
- 課題がまだ 1 件もなく、今決めれば移す手間がない

## 影響

- AI が Issues を読むには、開発用コンテナで `gh` を使えるようにする必要がある。使えないときは、人が Issue の内容を貼る
- Issue の作成・編集・クローズは GitHub への書き込みなので、AI は人の OK をもらってから行う（[06_課題・ロードマップ/README](../06_課題・ロードマップ/README.md) の「6」）
- コミットメッセージの 1 行目に Issue の番号を付ける（[08 コーディング規約](../02_共通設計/08_コーディング規約.md) の「5.1」）
- **見直す条件:** `gh` が使えない環境で作業することが多くなり、AI が課題を読めないことが妨げになったら、案 A か B を考え直す

# ADR-006 CI の通過をマージの条件にし、カバレッジの目標はドメイン層とユースケースだけに置く

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 採用 |
| 日付 | 2026-09-23 |
| 決めた人 | |

## 背景

テストツールを決めた（[ADR-005](./ADR-005_テストツール.md)）あと、テストをいつ・どこで実行するか、カバレッジの目標を置くかを決める必要があった。リポジトリは GitHub で管理している。

## 決定

- GitHub Actions で、Pull Request と `main` への push のたびに Lint・ファイル名のチェック・型チェック・テスト・ビルドを実行する
- CI が通っていない Pull Request は `main` にマージできないようにする（GitHub のブランチ保護）
- カバレッジの目標は、ドメイン層（`src/domain/`）とユースケース（`src/application/`）だけに置き、行・分岐・関数・文それぞれ 80% 以上にする
- 未使用コードの検出（knip）は、開発の初期は参考にとどめ、指摘が 0 件になったら必須にする

## 検討した案

### CI

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. CI で必ず通す（採用） | 壊れたコードが `main` に入らない。実行し忘れがない | 急ぎの修正でも、テストを直すまでマージできない |
| B. CI で実行するが必須にしない | 結果は見える | 失敗したままマージされ、放置されがち |
| C. 手元でだけ実行する | 設定がいらない | 実行し忘れる。人によってばらつく |

### カバレッジ

| 案 | 良い点 | 悪い点 |
| -- | ------ | ------ |
| A. 目標を置かない | 数値を上げるためだけのテストが増えない | テストを書かなくても気づけない |
| B. 重要な層だけに目標を置く（採用） | 業務のルールと認可という一番大事な部分の漏れに気づける。依存が少なくテストしやすい層なので無理なく届く | 対象を設定で指定する手間が少しある |
| C. 全体に目標を置く | 書き漏れが減る | 画面は E2E で確認する方針なので Vitest の数値が伸びにくく、意味の薄いテストが増えやすい |

## 理由

- GitHub で管理しているので、追加のサービスなしで CI を入れられる。テストが少ないうちに入れる方が、後から入れるより楽
- この構成ではテストの中心がドメイン層とユースケースなので、そこに絞れば意味のあるテストで自然に届く数値になる

## 影響

- 型チェックでは、先に `next typegen` でルートの型を作る（`next-env.d.ts` を Git で管理していないため）
- テストが 0 件でも CI が通るように `passWithNoTests` にしている。テストがそろったら外してよい
- GitHub のブランチ保護は画面で設定する必要があり、設定したかどうかを [11 CI](../02_共通設計/11_CI.md) の「4.2 設定状況」に記録する

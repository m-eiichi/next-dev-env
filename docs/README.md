# docs

このプロジェクトの要件定義と設計の資料。開発の始め方は、ルートの [README.md](../README.md) を参照。

## 読む順番

上から順に「何を作るか」→「どう作るか」→「細かいルール」→「画面ごとの詳細」になっている。`04_設計判断` は、それらのルールを決めた理由の記録。

| フォルダ | 内容 | 主に読む人 |
| -------- | ---- | ---------- |
| [00_要件定義](./00_要件定義/) | **何を・誰のために・なぜ作るか**。目的、機能要件、非機能要件、業務フロー | 全員。依頼者・企画担当と合意する内容 |
| [01_全体設計](./01_全体設計/) | **どう作るかの全体像**。画面一覧、技術スタック、データ、アーキテクチャ、ディレクトリ構成 | 開発者 |
| [02_共通設計](./02_共通設計/) | **画面をまたぐ実装のルール**。認証、データ取得、エラー処理、コーディング規約、テスト、CI など | 開発者（実装前に読む） |
| [03_画面設計](./03_画面設計/) | **画面ごとの詳細設計**。テンプレートをコピーして 1 画面 1 ファイルで書く | 開発者・デザイナー |
| [04_設計判断](./04_設計判断/) | **決めたことの理由**（ADR）。何を検討して、なぜそう決めたか | 開発者（方針に疑問があるとき、見直すとき） |

## 資料を書くときのルール

- 番号付きのファイル名（`01_概要.md` など）にし、各フォルダの README の表にも追加する
- 使わない資料は消してよい。消したら README の表とリンクも消す
- 同じ内容を 2 か所に書かない。片方に書き、もう片方からはリンクする
- 決まっていない項目は空欄や「◯」のまま残し、決まったら埋める。更新したら各ファイルの最後の「変更履歴」にも書く

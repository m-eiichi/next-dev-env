# コミットメッセージを作って、コミットする

メッセージのルールは `docs/02_共通設計/08_コーディング規約.md` の「5.1 コミットメッセージ」。ここには手順だけを書く。

- 頼まれたときだけコミットする（`docs/05_AI駆動開発/01_方針・進め方.md`）。push はしない（頼まれたら、別に確認する）
- 共同作成者の行（`Co-Authored-By:`）は付けない。Claude Code の既定の案内より、このプロジェクトのルールを優先する

## 1. 変更を確かめる

```bash
git status --short
git diff --staged --stat
git diff --stat
git log --oneline -5
```

- 今のブランチが `main` なら、作業ブランチ（`feature/xxx`、`fix/xxx`）を切るかをユーザーに確かめる（08 コーディング規約の「5」）
- 変更がなければ、そう伝えて終える

## 2. コミットするファイルを決める

| 状態 | コミットするもの |
| ---- | ---------------- |
| ステージ済みのファイルがある | ステージ済みのものだけ（ユーザーが選んだものとみなす） |
| ステージ済みのファイルがない | 変更をすべて。ただし下の「入れないもの」を除く |

- **入れないもの:** `.env` など秘密の情報が入りうるファイル、ビルドの結果（`.next/`、`coverage/`）。`.gitignore` にないのに変更に出ていたら、ユーザーに伝える
- **分けるとき:** 関係のない変更が混ざっていたら（例: 画面の追加と、関係のない設定の変更）、分け方（ファイルのまとまりと、それぞれのメッセージ）を提案し、分けるかどうかをユーザーに確かめる
- 差分の中身は `git diff`（`--staged`）で読む。ファイル名だけで種類や内容を決めない

## 3. メッセージを作る

08 コーディング規約の「5.1」に沿って作る。特に次を守る。

- 種類は、ファイルの場所ではなく「一番主な変更」で決める（`.claude/` だけの変更は `chore`、CI の変更は `ci`、資料だけなら `docs`）
- 1 行目は日本語で「〜を追加」「〜を修正」のように終え、句点とバッククォートを付けない。60 文字くらいまで
- 変更が複数あるときだけ、空行の後に `- ` の箇条書きで本文を書く（句点なし、3〜7 行）
- 迷ったら `git log` の、ルールに合っている過去のメッセージにそろえる。ルールに合っていない過去のメッセージは真似しない

## 4. 提案して、コミットする

1. ユーザーに、コミットするファイルの一覧とメッセージを見せる
2. 続けて、ファイルを `git add`（パスを並べる。`git add -A` / `git add .` は使わない）し、メッセージをそのまま渡してコミットする

```bash
git add <ファイル…>
git commit -F - <<'EOF'
<種類>: <何をしたか>

- <主な変更>
EOF
```

- `git commit` は権限の設定で必ず確認が出る（`.claude/settings.json` の `ask`）。**この確認を、メッセージの承認として使う**。ユーザーが拒否したら、直したい点を聞いて 3 から出し直す
- 権限の設定が変わって確認が出ない状態なら、1 の後にユーザーの「OK」を待ってからコミットする
- `--no-verify`、`--amend`、`git push` は、頼まれないかぎり使わない

## 5. 結果を伝える

```bash
git log -1 --stat
```

コミットした内容（ハッシュ、1 行目、ファイルの数）を短く伝える。コミットされずに残っているファイルがあれば、それも伝える。
